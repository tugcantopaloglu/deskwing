## iOS: validate without signing credentials

1. Push the reviewed source and keep the regular simulator/Windows verification green.
2. A push to the dedicated `codex/workspace-expansion` development branch runs only unsigned validation, so the new archive path can be checked before merging it into `main`. You can also manually run **Prepare iOS beta** with `mode=unsigned-validation`. The build uses the hosted `macos-26` runner, validates the AppIcon, runs the helper policy tests and creates a generic iOS Release archive with signing disabled. Branch pushes cannot enter the signing job or read its environment secrets.
3. Record the workflow URL and source SHA. Success establishes an unsigned device archive build. It does not establish an IPA, provisioning, installation or TestFlight.

New manual workflows may need to exist on the repository's default branch before GitHub exposes dispatch. The restricted unsigned branch trigger provides pre-merge validation without weakening the main-only manual signing controls. Keep the existing simulator workflow available as well.

## iOS: export a signed IPA for review

Create a GitHub environment named **`ios-beta`**. Restrict it to `main`, configure a required reviewer where the repository plan supports that protection, and add the following settings using GitHub's secure environment UI or approved secure administration tooling:

| Type | Name | Value |
| --- | --- | --- |
| Variable | `IOS_TEAM_ID` | The owner's 10-character Apple Team ID |
| Variable | `IOS_BUNDLE_ID` | `app.deskwing.tablet`, confirmed as the owner's registered app/bundle ID |
| Secret | `IOS_DISTRIBUTION_P12_BASE64` | Base64 of the Apple Distribution certificate/private key export |
| Secret | `IOS_DISTRIBUTION_P12_PASSWORD` | Its export password |
| Secret | `IOS_APP_STORE_PROFILE_BASE64` | Base64 of the matching App Store distribution provisioning profile |

Never paste these secret values into a chat, issue, workflow input or source file. The workflow generates its temporary keychain password, imports material in runner temporary storage, checks profile/team/bundle/expiry/distribution entitlements and certificate membership, and removes the temporary keychain and profile in cleanup.

Run **Prepare iOS beta** from `main` with `mode=signed-archive` and the approved `build_number` (default 18). The artifact contains the exported IPA, SHA-256 checksums and non-secret manifest. It excludes signing material and full build logs. The workflow never calls an App Store upload tool, and it needs no App Store Connect API key.

Before an owner uploads that IPA, verify the app record, selected countries/pricing, age rating, privacy and encryption answers, actual screenshots, support/privacy URLs and beta-review information. An internal TestFlight upload and the applicable external-beta review remain owner-controlled steps. [Apple's TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/) describes the distribution stages.

## Android: prepare a Play bundle

The separate **Prepare Android beta artifacts** workflow defaults to `unsigned-validation`. Pushes to the dedicated `codex/workspace-expansion` branch run unsigned package validation without reading signing secrets; signing remains a manual `main` operation. For an upload-key-signed candidate, create a protected **`android-beta`** environment restricted to `main` and configure:

| Type | Name | Value |
| --- | --- | --- |
| Variable | `ANDROID_UPLOAD_KEY_ALIAS` | Alias inside the upload keystore |
| Variable | `ANDROID_UPLOAD_CERT_SHA256` | Expected public upload-certificate SHA-256, 64 hexadecimal characters |
| Variable | `ANDROID_LAST_PUBLISHED_VERSION_CODE` | The actual latest Play upload code, or zero only if this app has never been uploaded |
| Secret | `ANDROID_UPLOAD_KEYSTORE_BASE64` | Base64 of the intended Play upload keystore |
| Secret | `ANDROID_UPLOAD_KEYSTORE_PASSWORD` | Keystore/key password used by this build path |

Run `mode=signed-beta` only after reviewing the Play App Signing enrollment. The workflow uses pinned/hash-checked Android tools and the existing APK/AAB/parity build, verifies package/SDK/version and the expected signer, and stages only the bundle deliverable and non-secret metadata. Treat any universal APK in validation output as upload-key-signed validation material; do not distribute it over the existing direct installation unless its signing identity is compatible.

Keep Play-installed apps on the Play update path. The expansion's PC USB updater blocks both automatic and manually confirmed replacement of Play-managed installations, other store owners and unknown/malformed origins before download. Known shell/local-install provenance can use the direct original-signer path; a null installer field alone is not sufficient. The updater rechecks source, version and the selected tablet immediately before installation, including for a cached APK. Initial installation on a tablet without the app remains a separate explicit setup path. Rehearse these boundaries in the exact candidate before distribution. [Google's testing guide](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en) recommends starting internally, then widening testing after feedback.

## Hardware and review evidence

Use an explicit source/build matrix rather than carrying earlier results forward automatically:

| Check | Evidence required for this candidate |
| --- | --- |
| Existing installation | Board/page/button IDs and content, pairing and signing continuity retained after upgrade; no uninstall-first workaround |
| Android tablet | First run, denied/allowed camera, rotation/resizing, pen/palm/IME, notes/PDF/history, USB/Wi-Fi interruptions and actual audio output |
| Native display/input | Selected source/quality, received/rendered counters, explicit input permission, pressure/geometry, stop/background/revocation and failure recovery |
| Physical iPad/Pencil | Signed install, local-network permission, pinned pairing, Pencil/Scribble, PDF export, foreground/background and actual video/input |
| Privacy | Inspect final dependencies/network behavior, note/PDF/history deletion and diagnostic redaction; verify the public policy/support URLs |
| App Review hardware demo | Camera-recorded video of the app on a physical Apple device pairing and interacting with the required Windows PC |

Apple asks hardware-dependent apps for a physical-device video rather than a screen recording. [Complete-review guidance](https://developer.apple.com/help/app-review/before-submitting-for-review/complete-review/) explains the review information. Keep simulator results, physical results and signed-export/upload evidence distinct.
