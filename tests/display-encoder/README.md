# Windows H.264 encoder checks

`dotnet run --project tests/display-encoder/DisplayEncoderTests.csproj -c Release` runs 54 deterministic pixel-conversion, bounds, H.264 configuration, retry-window and native layout/reference checks without capture, input injection or encoder activation. The COM reference test verifies cleanup of all 300 rejected inventory entries, including entries beyond the activation-attempt limit.

Add `-- --native` to choose a compatible Windows Media Foundation H.264 hardware encoder, with software compatibility fallback, on synthetic moving pixels. Options include `--width 1920 --height 1080 --rate 144 --frames 240`, `--software` to select software explicitly, and `--change-bitrate` to request a 4 Mbps target during encoding. Output includes the actual encoder name, hardware flag, accepted bitrate and fallback reason. `--output <path>` optionally writes the synthetic Annex B bitstream for independent decoder inspection. The probe never reads the desktop or any window. It checks one output access unit per input, unchanged capture timestamps, bounded frames and SPS/PPS on each IDR.

Add `--force-idr` to that native probe to verify that a recovery request makes the very next frame an IDR carrying SPS/PPS after a 500 ms timestamp gap. The encoder uses Microsoft's [single-frame force-keyframe property](https://learn.microsoft.com/en-us/windows/win32/medfound/codecapi-avencvideoforcekeyframe), so a decoder waiting for a clean starting point can recover on the first update after an idle period.

The production encoder uses Baseline, no B frames, a one-second GOP and low-latency controls. [Hardware MFT enumeration](https://learn.microsoft.com/en-us/windows/win32/api/mfapi/nf-mfapi-mftenumex) honors Windows' sorted/filtered inventory; compatible hardware uses the [asynchronous input/output event contract](https://learn.microsoft.com/en-us/windows/win32/medfound/asynchronous-mfts). Hardware probing has a 1.5-second managed wait budget, four activation attempts, bounded event credits and session cancellation. Native driver calls remain operating-system calls. Unsupported initialization or a failed first frame falls back before publishing any picture. A failure after published pictures ends that session and skips the failed encoder/format for five minutes on fresh sessions. Length-prefixed hardware configuration/access units are validated and normalized to Annex B. Bitrate changes are applied only when the codec accepts the request. No bundled third-party codec is needed. Each instance belongs to one stream worker thread and accepts bounded positive-stride BGRA frames; capture authorization belongs to the separate display service.

The 2026-11-06 synthetic 1280×800/120 probe on this PC selected **NVIDIA H.264 Encoder MFT**, emitted all 60 access units, accepted a change from 20.48 Mbps to 4 Mbps and produced the requested recovery IDR with SPS/PPS. Mean color-conversion-plus-encode time was 6.83 ms, p95 9.31 ms. An explicit software probe emitted the same count and accepted the same change, with 5.88 ms mean and 6.72 ms p95. These short workload samples establish availability and API behavior; capture, network, decoder, presentation, power and sustained performance require their own measurements.

`-- --native --native-lifecycle` exercises eight codec create/first-keyframe/cancel/dispose cycles, rejects foreign-thread input, and verifies that cancelled sessions produce no further frame. It uses synthetic pixels only. Both hardware and software paths retain cancellation-safe cleanup.

Local synthetic measurements on 2026-11-05 (Ryzen 5 7500F): 1280×800 at a requested 60 Hz encoded 600 frames with 2.82 ms mean and 5.32 ms p95 time for color conversion plus encoding. A 1920×1080/144 Hz probe encoded 240 frames with 5.45 ms mean and 10.60 ms p95. These measurements exclude capture, transport, decoding and screen presentation, so they do not establish end-to-end refresh rate. The separate stream and tablet counters must report actual performance.

The 1080p synthetic stream decoded as 240 constrained-Baseline frames using an independent local FFmpeg installation. Raw Annex B has no transport timestamps; supply the requested input rate when inspecting it (`ffmpeg -r 144 -i <path> -f null NUL`). The live protocol carries capture timestamps explicitly.

Interface declarations are derived from the installed Windows SDK headers. Encoding follows Microsoft's [H.264 encoder documentation](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder), [sample processing contract](https://learn.microsoft.com/en-us/windows/win32/medfound/processing-data-in-the-encoder) and [Annex B sequence header format](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-mt-mpeg-sequence-header-attribute).

`-- --native-resources` allocates and disposes 100 persistent capture contexts and 100 cursor composition contexts, queries a shared standard cursor 1,000 times, and verifies that the process GDI-handle count returns to its baseline. It never invokes capture. The capture implementation follows the [CreateDIBSection synchronization requirement](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createdibsection): finish the GDI batch before copying bitmap memory. Its reusable top-down BGRA buffer avoids per-frame bitmap/graphics allocation and `LockBits`; the separate stream service authorizes the exact owned display rectangle before and after capture.

The hardware cursor is composited only when its visible anchor lies inside that rectangle. Hotspot offsets use physical pixels, and the display-sized DIB clips cursor artwork at its edges. Bitmaps allocated by [GetIconInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-geticoninfo) are released after every query; the shared system cursor handle remains untouched. Pure tests cover negative monitor origins, every included/excluded edge, hotspot offsets and integer-overflow rejection.

The DXGI cursor overlay reads only the supplied frame buffer and cursor resource. It does not read a screen DC. Each call must receive fresh base pixels, including mouse-only acquisition updates, so the previous cursor cannot leave a trail. Cursor composition runs only when DXGI reports a separate visible pointer; an already-composited pointer is not drawn twice. The default pure checks also verify DXGI interface layouts and bounded copies from padded and tightly packed GPU rows.
